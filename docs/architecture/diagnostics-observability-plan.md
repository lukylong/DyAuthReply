# 客户端诊断可观测性优化方案（2026-10-21）

## 目标与已知问题
- 接收补拉失败 70 条上报缺 reason，无法细分失败原因。
- 自动回复只报告账号/规则，缺触发类型及批次关联；无法确认回关触发后是否取得回执。
- 发送分段缺序号和类型，部分送达时难以区分是哪一段失败。
- 自动回复暂停缺配置变更来源，历史告警易与最新状态混淆。
- 运行事件仍有英文原文、错误类别与建议不明确。

## 方案与边界
1. 客户端补齐 reason；接收失败额外提供静态阶段、类型化 HTTP/业务状态、网络/解析/存储错误摘要。未知错误只记固定提示，不直接序列化任意错误链或响应正文。
2. 自动回复入队记录 trigger_type=mutual_follow/message；发送事件标识 message_source=automatic/manual。
3. batch_id 仅在本地日志存在；上传时用带域分隔的 SHA-256 前 16 个十六进制字符生成 trace_id。同一批次跨分段、重试、重启保持一致。
4. 发送事件记录 segment_index/segment_count、content_kind=text/link、content_chars、attempt。类型仅描述本地文本段或纯链接段，不猜测是否已被平台渲染成卡片；无正文/URL/收件人标识。
5. 批次停止记录相同关联号和原因；账号自动回复配置变更记录 enabled/previous_enabled/change_source，只有实际持久化变更才发事件，不将运行时暂停一概归因于用户。
6. 后台分类为自动回复、发送、接收、授权、登录、媒体或运行；显示中文标题、影响和下一步建议，完整技术原文仍可展开。
7. 支持设备范围内按匿名账号、关联号及触发类型服务端筛选。触发筛选针对触发事件；点击关联号清除触发筛选后查看整个批次的记录，不凭相邻时间强行拼接。
8. 展示发生和接收时间；保留最新快照与历史事件的区分、35 分钟过期规则。无旧字段时显示来源/关联未上报，绝不猜测。

## 数据兼容与发布
- 使用现有 JSON fields；不改数据库结构、发送判定、业务路由格式、凭证和重试策略。
- 后端先部署可兼容旧客户端；旧后端会丢弃新键，因此客户端和后台上线需要协调。
- 默认诊断开关和用户已关闭选择保持不变；15 分钟频率、500 条上传批量、缓冲上限/30 天保留策略不扩大。
- 新关联号/枚举/计数字段由服务端校验，错误或未知值丢弃；无私信正文、昵称、Cookie、令牌或完整链接。
- 日志只证明该事件的阶段：入队不等于发送；成功回执不等于收件人可见正文；部分成功不宣称全批送达。
- 历史日志没有触发来源时无法回填或推断；本轮不发版、不改线上开关、不重试历史消息。

## 实施顺序及验收
1. 保存原始文件与哈希；先添加失败回归测试。
2. 客户端 reason/关联脱敏及业务事件生产者；新旧数据持久化兼容。
3. 服务端新字段约束、设备隔离查询过滤及兼容测试。
4. 管理端中文解释、时间、关联查看和过滤；测试旧日志/未知事件/部分失败。
5. Rust fmt/Clippy/单元与集成测试、Django 隔离测试、管理端构建与节点测试。
6. 原始副本与修改副本对照；独立副本验证回滚；工作区保留实现。临时模拟接口页面验证，不操作真实业务。

## 后续优先级
- P1：核对实际暂停来源、刷新长期未上报设备并处理真实登录失效，独立于日志功能上线。
- P2：获得新版链路日志后再定位 8101 内容/上下文问题；不将业务拒绝改标成功，不自动重发历史部分送达批次。
- P3：数据积累后评估重复事件去重、聚合和报告成功率；无唯一事件口径前不拿事件条数当成功率。
